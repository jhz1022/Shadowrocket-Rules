# 注册后缀收紧、DNS 容错与真实内容验收

2026-10-31，Mac Shadowrocket 2.2.93 / macOS 26.7.1。用户授权解决复审发现的缺口。

## 实际变更

- 国内原始源中的 52 条注册级/TLD 后缀不进入直连生成，包括 cn、中文通用顶级后缀及单标签品牌顶级后缀。所有单标签后缀统一排除；ac.cn、edu.cn、gov.cn 等列明的注册级后缀同样排除。保留源中明确列出的百度、淘宝、微信和其他业务域名。未知 `.cn` 现在默认 PROXY，解析不再仅凭 `.cn` 被分配给国内系统 DNS。
- 15 个精确 Apple 商店接口/图片/下载主机，7 个精确更新目录/恢复主机补入审查层。来源是 Apple 官方服务用途及固定归档中的 apple @cn / apple-update 分类；不放开整个 Apple、mzstatic、共享 CDN，也不承诺商店地区或媒体资格。部分商店资产跨服务共用，不能仅靠域名让每项业务的全部资源使用同一出口。
- 代理解析改成两个显式主 DoH：Cloudflare 与 Google，均带 #proxy。保留禁用系统回退和显式备用字段，但不再把备用字段的存在当作容错证明。
- audit_sources.py 独立读取原始归档、属性、include、affiliation、Clash 域名和 CIDR，不调用构建器的源解析、压缩或冲突处理函数。构建器源解析函数被禁止调用时审计仍能运行；故意把源中的 DOMAIN 错转为后缀，审计能够独立检出。它仍不是对上游分类真实性的外部认证，也不是原生 DNS/TUN 模拟器。
- 健康检查增加上游归档/停用、目标分支提交年龄检查：人工维护国内源预算 336 小时，每日产出源预算 72 小时。预算超限或 API 不可用即显示检查失败，不伪造更新或产生保活提交。提交活动不等于内容准确，也不能证明生产者内部的所有数据都新鲜。

## 真实 DNS 故障对照

仅使用本地测试副本，不修改节点凭据、系统 DNS、VPS 或系统时间。故障端点使用 RFC 5737 文档地址。用 TXT 避免把 Fake-IP 的 A 应答误认作解析器已经工作；随机不存在名称用于否定应答和失败对照。原始记录保存在本机 .build，不上传个人 DNS/代理日志。

| 配置/测试 | 实际观察 | 可以得出的结论 |
| --- | --- | --- |
| 旧单主失效，保留 Google 备用 | 正向 example.net TXT 与随机否定查询均在 8 秒内超时 | 旧备用设计未达到本轮容错目标，不再依赖它 |
| 双主：首端失效，Google 健康 | example.com TXT 有效，约 0.46 秒；原生 DNS 日志标明 Google #proxy | 本轮正向解析可以使用健康第二端 |
| 双主：Cloudflare 健康，第二端失效 | _spf.google.com TXT 有效，约 0.40 秒；原生日志标明 Cloudflare #proxy | 本轮反向对照也有效 |
| 所有代理 DoH 都失效 | example.org 正向控制及随机不存在名称均在 8 秒窗口内无 DNS 应答 | 本轮没有收到意外回退答案；不是无限时间或物理网卡零查询证明 |
| 恢复双主正常配置 | example.org TXT 约 0.43 秒，随机 NXDOMAIN 约 0.43 秒，均有效 | 恢复后正向与否定解析均恢复 |

保留反例：双主中一端黑洞失效时，随机 NXDOMAIN 查询也曾超过 8 秒；健康端有否定应答日志，不能把它冒充正向容错成功，也不能保证所有类型都快速失败。这是当前客户端观察到的否定应答等待边界，配置没有未经证实的“DNS 超时调节参数”。日常有效域名在本轮双向控制中正常。单节点仍是共同故障点，两家 DoH 不能代替备用节点。

公开 IPv4 UDP/53 五项仍返回 Fake-IP；三项公共 TCP/53 与两项 IPv6 UDP/53 无上游答案。公共 TCP/53 保持 REJECT 的设计：本机未验证到可把它透明转换成 DoH 的可靠配置语法，不能改成放行国内公共解析器来伪装兼容。应用自带硬编码 TCP DNS 仍可能失败，应采用系统解析；任意 DoH/DoT、私网旁路和 Tunnel 外流量不在这条端口规则的全面保证范围内。

额外生成未收录的随机 `.cn` 名称进行真实 TXT 查询：约 1.94 秒收到 NXDOMAIN；原生 DNS 日志同时记录 Cloudflare / Google 的 #proxy 路径，没有因为 `.cn` 后缀选择系统直连解析。这是本轮具体查询证据，不推广为所有域名和应用都已验证。

## 真实业务对象

scripts/probe_apple_delivery.py 是可重复的 Mac 可选验收，不在 Actions 上冒充客户端测试：

1. 请求 Apple 商店 lookup 接口，返回指定微信 App 的公开元数据。
2. 使用响应给出的 is1-ssl.mzstatic.com 图片地址，完整下载 148,257 字节 PNG，HTTP 200，TLS 校验开启。
3. 下载并解析 swscan.apple.com 的真实 Rosetta 更新目录；选取一个不超过 20 MiB 的最新可用包。
4. 从 swcdn.apple.com 完整下载 494,571 字节的包，大小与目录一致；验证目录中的压缩 XAR TOC 摘要、122 项包内存档数据校验值，再由 pkgutil 确认 signed Apple Software。目录 Digest 在此为压缩 TOC 摘要，不能错误地与整个包的 SHA-1 比较。
5. 原生代理日志核对上述四个主机均命中精确 DOMAIN / DIRECT。包没有安装、执行或接受许可。

这验证一条真实对象链，不等于每个 App、每个系统版本或完整安装升级验收。指定下载速度也不是跨网络的性能保证。另一次 13 项公开 HTTP 协议检查完成，中国 NTP 五项应答有效；Apple 校时有单次超时，原始失败保留。

```bash
python3 scripts/probe_client_dns.py --resolution success
python3 scripts/probe_client_dns.py --resolution negative
python3 scripts/probe_apple_delivery.py
```

故障测试必须在可恢复的本地副本中修改两个显式主端点，再按表中的正向/否定请求检查原生日志；禁止直接将故障端点发布到 dist 或让用户日常使用它们。

## 不能靠增加规则消除的边界

- 国内业务的完整分类没有绝对真值；收紧泛后缀提高保守性，同时可能让未收录国内服务默认代理。应以具体请求及归属证据迭代，不按后缀重新全放行。
- IPv4 模式保留微信已验证修复。当前物理网络和 VPS 缺少完整 IPv6 条件，不能通过配置制造不存在的 IPv6 出口；iPhone 蜂窝、IPv6-only/NAT64、长期性能仍需对应环境。
- 本轮没有关闭正在承载电脑联网的节点或 Wi-Fi 来做破坏性断网，未将“重载配置恢复”写成“网络切换/节点断线已验证”。也未取得管理员物理网卡抓包。
- 同仓库健康检查无法监控 GitHub 完全不执行任务的情况。GitHub 延迟、停用及全平台故障仍须平台通知或外部观察；不制造无意义提交，不额外部署违背本项目约束的客户端后台任务。
- 规则不决定节点出口信誉、地区、原生 IP 或 Netflix/AI 的账户授权。

# 微信头像和图片慢：IPv4 兼容修复

日期：2026-10-31，Asia/Shanghai。环境：macOS 26.7.1 / Shadowrocket 2.2.93，“配置”模式，原有首页节点。

## 故障与证据

用户最初描述聊天列表/收发慢。进一步让用户向文件传输助手发送测试消息，用户反馈文字消息很快，主要是图片和头像加载非常慢。聊天记录导入进行中，但用户确认此前已经慢，不能把故障直接归因于导入。

- 常用消息、图片和头像域名在规则模型中为 DIRECT。对应消息长连接的实际出口位于物理接口 en0，并非只根据模型推测；该连接 RTT 约 54–60 ms，短时采样未发现重传。
- 微信图片请求出现多条公网 IPv6 连接；隧道进程对应的物理出口持续处于 SYN_SENT，接收字节为零。相同期间，IPv4 图片连接已建立并接收数据。
- 物理网卡当时只有 fe80 链路本地 IPv6 地址，没有公网 IPv6 地址；存在路由条目不等于具备可用公网 IPv6。客户端内侧的 ESTABLISHED 也不能证明隧道外侧已连接到目标。
- 本轮短时连接日志没有看到端口 53 拒绝命中，但这不覆盖所有历史请求，也不据此认证 DNS 完全无关。

以上将问题定位到当前网络的不可用 IPv6 路径及应用等待，而非仅凭 VPS 未启用 IPv6 或“微信域名应该直连”判断。

## 单项对照与结果

在现用配置中仅将 `ipv6 = true` 改为 `ipv6 = false`，保留 `prefer-ipv6 = false`、全部分流和 DNS 防护规则。没有修改系统网络设置、节点、账号或聊天缓存，没有退出微信或主动取消聊天记录导入。

保存配置会重载网络连接，因此不能声称所有既有连接完全未受影响。变更后：

- 头像域名在本机的 AAAA 查询返回映射到 IPv4 的地址。
- 微信新的资源连接改为 IPv4。
- 用户再次打开原先慢的头像/图片，明确反馈：**“明显恢复，加载很快”**。

当前证据强烈支持不可用 IPv6 路径造成资源加载等待。但保存配置也重建了连接；没有再次开启故障设置做反向 A/B，不宣称已经排除全部缓存或重连因素。

公开 CDN 根路径探测中，wx.qlogo.cn 和 mmbiz.qpic.cn 的 TLS 成功，HTTP 400 分别约 0.12 / 0.20 秒；wx.qpic.cn 根路径 TLS 探测失败。这些只用于协议连通性对照，不冒充私人头像和图片下载成功的自动认证。真实使用改善来自用户反馈及实际连接变化。

## 固化与边界

模板和构建校验器采用 `ipv6=false`、`prefer-ipv6=false` 的 IPv4 兼容基线。新增微信消息与资源域名的路由哨兵，阻止上游变更静默地将它们改走代理；没有添加广告规则或宽泛的腾讯 IP 旁路。

国内 IPv6 前缀及局域网排除仍保留，便于审计及以后经过验证的部署。关闭客户端选项不是系统级 IPv6 防火墙，不等于给 VPS 修好了 IPv6。若未来启用原生 IPv6，应同时验证本地直连、节点出口和 DNS，再配套调整模板、校验器与验收记录。iPhone、IPv6-only/NAT64 和网络切换仍待实测。

首轮只确认 VPS 未开 IPv6 后仍保留客户端 IPv6 启用，遗漏了本地直连出口检查；本记录明确纠正该判断。国内精确直连例外仍是研究草案，没有混入本次修复。

原始连接数据仅保存在本机；公开仓库不包含聊天内容、个人出口地址、节点凭据或手机导入记录。

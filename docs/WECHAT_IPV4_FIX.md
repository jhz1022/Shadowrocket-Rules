# 微信头像和图片慢：IPv4 兼容修复

日期：2026-10-31，Asia/Shanghai。环境：macOS 26.7.1 / Shadowrocket 2.2.93，“配置”模式，原有首页节点。

## 故障表现

最初表现为微信使用卡顿。向文件传输助手发送消息后，确认文字收发正常，主要是图片和头像加载很慢。当时正在导入聊天记录，但问题在导入前就已出现，不能直接归因于导入。

- 常用消息、图片和头像域名在规则模型中为 DIRECT。对应消息长连接的实际出口位于物理接口 en0，并非只根据模型推测；该连接 RTT 约 54–60 ms，短时采样未发现重传。
- 微信图片请求出现多条公网 IPv6 连接；隧道进程对应的物理出口持续处于 SYN_SENT，接收字节为零。相同期间，IPv4 图片连接已建立并接收数据。
- 物理网卡当时只有 fe80 链路本地 IPv6 地址，没有公网 IPv6 地址；存在路由条目不等于具备可用公网 IPv6。客户端内侧的 ESTABLISHED 也不能证明隧道外侧已连接到目标。
- 本轮短时连接日志没有看到端口 53 拒绝命中，但这不覆盖所有历史请求，尚不能排除 DNS 因素。

连接记录提示，图片请求可能在等待不可用的 IPv6 路径；下面通过单项设置对照验证。

## 单项对照与结果

仅将现用配置中的 `ipv6 = true` 改为 `ipv6 = false`，保留 `prefer-ipv6 = false`、全部分流和 DNS 防护规则。没有修改系统网络设置、节点、账号或聊天缓存，没有退出微信或主动取消聊天记录导入。

保存配置会重载网络连接。变更后：

- 头像域名在本机的 AAAA 查询返回映射到 IPv4 的地址。
- 微信新的资源连接改为 IPv4。
- 重新打开原先慢的头像和图片，**加载速度明显恢复**。

当前证据强烈支持不可用 IPv6 路径造成资源加载等待。但保存配置也重建了连接；未再次开启故障设置做反向 A/B，因此仍不能排除缓存或重连的影响。

公开 CDN 根路径探测中，wx.qlogo.cn 和 mmbiz.qpic.cn 的 TLS 成功，HTTP 400 分别约 0.12 / 0.20 秒；wx.qpic.cn 根路径 TLS 探测失败。这些探测仅检查协议连通性。头像和图片的加载结果来自实际打开前后的对照，并结合连接变化判断。

## 配置调整与后续测试

模板和构建校验器采用 `ipv6=false`、`prefer-ipv6=false` 的 IPv4 兼容基线。新增微信消息与资源域名的路由哨兵，阻止上游变更静默地将它们改走代理；没有添加广告规则或宽泛的腾讯 IP 旁路。

国内 IPv6 前缀及局域网排除仍保留，便于审计及以后经过验证的部署。关闭客户端选项不是系统级 IPv6 防火墙，不等于给 VPS 修好了 IPv6。若未来启用原生 IPv6，应同时验证本地直连、节点出口和 DNS，再配套调整模板、校验器与验收记录。iPhone、IPv6-only/NAT64 和网络切换仍待实测。

首轮排查只确认了 VPS 未开 IPv6，遗漏了本地直连出口，因而保留了客户端 IPv6。此次对照测试后改为 IPv4 兼容设置。国内精确直连例外仍是研究草案，没有混入本次修复。

原始连接数据仅保存在本机；公开仓库不包含聊天内容、个人出口地址、节点凭据或手机导入记录。

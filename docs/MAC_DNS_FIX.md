# macOS DNS 修复与 IPv6 排查

日期：2026-10-31（Asia/Shanghai）。环境：macOS 26.7.1，Shadowrocket 2.2.93，全局路由为“配置”，使用首页已选择的 VLESS 节点。未读取或发布节点凭据；未更改节点服务器。

## 根因及修复

初版使用不带端口的 `hijack-dns` IP 名单。主动向国内公共 DNS 查询 `www.google.com` 时，连接日志显示 UDP/53 命中国内 IP 的 DIRECT 规则，收到的地址注册归属为 Twitter / Facebook，而非 Google。这是主动诊断请求产生的旁路证据，不等于已证明普通浏览器的 Google 请求自动泄漏。

在保留原配置作回退的情况下，先导入本机候选进行单变量对照：

| 候选 | IPv4 UDP DNS | TCP DNS | 结果 |
| --- | --- | --- | --- |
| 原裸 IP 名单 | 国内目标仍直连到上游 | 可直接查询国内上游 | 未通过 |
| 明确 `IP:53` | 已列地址返回 Fake-IP | 仍可能查询上游 | 仅修复了已列 UDP |
| 空地址 `:53` + 兜底 | 本机未透明接管，落入拒绝 | 无上游答案 | 未选用 |
| **`*:53` + 端口 53 拒绝兜底** | **已列及未列 IPv4 地址均返回 Fake-IP** | **无上游答案** | **最终方案** |

最终配置：

```ini
[General]
hijack-dns = *:53

[Rule]
# 先保留完整的局域网规则，然后：
DST-PORT,53,REJECT
# 再匹配代理域名、国内域名、国内 IP，最后 FINAL,PROXY
```

`DST-PORT,53,REJECT` 是对没有被客户端 DNS 处理器接管的流量进行拒绝，不是 TCP DNS 透明代理。它必须位于中国 IP 直连规则之前，否则硬编码国内 DNS 仍会提前命中 DIRECT。局域网规则及 TUN 私网排除保留在前，以兼容局域网 DNS、设备发现及私有业务。

客户端内部的系统 DNS / DoH、节点引导，以及应用发到外部 DNS 地址的端口 53 连接属于不同层次。国内网页、海外网页和节点当前连接均在候选下复测；不把关闭全部 DNS 或屏蔽检测站作为修复。

## 实时探测结果

运行 `python3 scripts/probe_client_dns.py`：

- IPv4 UDP：`8.8.8.8`、`223.5.5.5`、`119.29.29.29`、`9.9.9.9`、`114.114.114.114` 查询 Google，全部返回 `198.18.0.0/15` 内的 Fake-IP。
- TCP：对 Google、阿里和腾讯 DNS 的定向查询无上游答案，连接被关闭。
- IPv6 UDP：对 Google 和 Cloudflare DNS 的定向查询无上游答案；随后在本轮原生“拒绝”日志中确认这两项及三项 TCP 查询均命中 `DST-PORT,53,REJECT`（候选 11:11:59 / 11:12:15；正式 GitHub 订阅 11:18:33）。这证明本轮端口拒绝规则实际执行，不是 IPv6 透明接管成功；仍未做物理网卡抓包。
- 复测百度、淘宝 HTTP 200，Google 204、GitHub 200；其余业务请求与初轮结果对照，无新的连接层失败。
- 修订候选下再次运行 BrowserLeaks DNS：67 个 Google LLC / Cloudflare 出口，均为美国；没有观察到中国解析出口。此前 WebRTC 和视频测试结果见验收记录；不上传含个人出口地址的原始日志。

探测器会区分真实 DNS 应答与“无应答/连接关闭”，不会把 NXDOMAIN 或 SERVFAIL 当成拒绝成功。无答案本身仍不能单独证明包未外发，需结合客户端规则、对照结果和日志；本次没有管理员物理网卡抓包。

## 首轮 IPv6 排查（历史结论，后续已修正）

普通 Google IPv4 访问成功，但以下两类均失败：

- 带正确 SNI 的 Google / Cloudflare IPv6 字面量目标。
- 仅有 IPv6 的域名目标，而不仅仅是 IPv6 字面量。

用户随后确认 VPS 未启用 IPv6。这与观测相符：客户端的 `ipv6 = true` 只能提供本地 IPv6 处理能力，不能给 IPv4-only VPS 增加 IPv6 出口。没有 SSH 登录服务器或宣称已经修复服务器的 IPv6 路由。

首轮保留 `ipv6 = true`、`prefer-ipv6 = false` 和国内 IPv6 前缀，继续使用稳定的 IPv4 节点访问双栈服务。纯 IPv6 目标仍受节点能力限制；如确有需要，应先在 VPS 服务商和系统中启用 IPv6、同步防火墙，再复测。没有为了让检测表变绿而声称“关闭 IPv6 即修复”。

## 自动化回归

构建器固定检查 `hijack-dns = *:53`、DNS 拒绝兜底的精确内容和顺序。新增测试覆盖：

- 外部 IPv4/IPv6 的端口 53 进入拒绝兜底，局域网 DNS 保留 DIRECT。
- 普通 HTTPS 的国内/海外分流不受该规则影响。
- 删除、移动、改成 DIRECT、改错端口或退回无效接管写法时构建失败。
- 上游仍不能注入任意 REJECT 域名或广告拦截规则。

本次不是 iPhone、网络切换、节点故障注入或“所有 DNS 协议均无旁路”的认证；应用自带 DoH/DoT、私网旁路和 Tunnel 之外的流量仍需单独评估。

正式订阅已从 GitHub 更新并生效，客户端解析 42,450 条规则；重复实时 DNS 探测及 25 站点连接检查通过上述限定范围。修订 CI：[41163723164](https://github.com/jhz1022/Shadowrocket-Rules/actions/runs/41163723164)。正式订阅下最后一轮 BrowserLeaks 为 70 个 Google/Cloudflare 美国出口。代理日志已恢复关闭，临时本机 HTTP 服务器已停止。

## 后续纠正：微信图片与本地 IPv6

首轮仅确认 VPS 未启用 IPv6，没有充分检查国内直连的 IPv6 出口。微信变慢后发现：文字消息快，头像/图片慢；物理网卡只有 fe80 链路本地地址，微信图片的公网 IPv6 连接持续 SYN_SENT。将现用配置改为 `ipv6 = false` 后，微信新连接转向 IPv4，用户明确确认“明显恢复，加载很快”。当前模板据此采用 IPv4 兼容基线。完整证据、限制及回归见 [WECHAT_IPV4_FIX.md](WECHAT_IPV4_FIX.md)。上文 IPv6 启用状态和拒绝日志是首轮历史记录，不是对新默认的原生 IPv6 能力认证。

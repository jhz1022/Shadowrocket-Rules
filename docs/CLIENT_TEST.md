# macOS / iPhone 客户端验收

当前版本已完成一次有备份和恢复措施的 Mac 实机验证，结果及未覆盖范围见 [本轮验证记录](MIXED_ROUTING.md)。下表是通用验收清单，不代表每项完整业务均已测试；历史 iPhone 结果只适用于当时配置。

目标是验证真实请求的规则及 DNS 路径，不能只看检测页颜色。建议只做下面这一轮有记录的验收；故障时保留证据，不反复盲改 DNS 或地区策略组。

## 准备（一次）

1. 记录 Shadowrocket 版本、系统版本、网络（家中 Wi-Fi/公司 Wi-Fi/蜂窝/热点）、节点协议、配置 `manifest.json` 的 `config_sha256`。节点地址、密码不用发到公开仓库。
2. 备份当前配置。添加本仓库唯一 `.conf` 订阅并启用；首页选一个已知可用节点，全局路由选择“配置”。确认旧模块、场景或本地 DNS 覆写没有改变本配置。
3. 在“数据”或当前版本的等价入口开启 **DNS 日志** 和 **代理/连接日志**。清空旧日志及客户端 DNS 缓存；重连一次。浏览器使用新窗口，排除旧连接复用。为了建立基线，首次测试记录并暂时关闭浏览器自带安全 DNS、Private Relay 及其他 VPN；最终还要恢复日常设置复测。
4. macOS 下记录实际的“代理类型”与 Tunnel 选项；先保持一种已能连接的模式完成测试，不把来回切换模式作为解决方案。之后才单独比较 TUN 路径。Include All Networks / Enforce Routes 会与本地网络排除相互影响，按当前版本内置说明记录，避免为一次测试盲目开启全部开关。

网页成功不等于分流正确：逐项打开连接详情，记录命中规则、策略、实际节点、目标 IP。检查子资源失败是否也有对应日志。未分类域名只有到达中国 IP 兜底层才允许触发路由解析；需要验证 Fake-IP 请求在原生客户端是否确实触发该过程。海外 DNS 仍可能返回海外 CDN，因此 IP 兜底不保证所有未收录国内服务都直连。

## DNS 检测与查询证据

1. 打开 [BrowserLeaks DNS](https://browserleaks.com/dns)，进行扩展测试；记录时间、检测到的解析器和 ASN。不要给此站及它临时生成的子域名单独添加代理/屏蔽规则。
2. 同时间核对 Shadowrocket **DNS 日志**中的测试随机域名、Google、GitHub、ChatGPT 域名：查询是否来自系统/客户端、是否有缓存、用了哪个 DNS 或远端解析。代理日志确认相应请求走选中节点。
3. 国内百度、淘宝查询出现在系统/国内 DNS 属于正常设计；节点域名出现在阿里 DoH 属于独立引导。测试站观察到中国解析器只是线索；必须把**具体应代理域名**与不期望的解析路径关联，才能判定本项目隐私目标失败。
4. 部分代理协议会直接发送域名到远端，此时可能没有对应的本地 DNS 上游日志。这不是自动通过；需结合节点解析日志或可控域名权威日志确定。也不能把代理节点使用的递归解析器当成设备直接发往它的证明。

如果日志不足，可在网关/路由器侧抓取测试设备流量，并在自己控制的域名上生成带时间随机前缀的查询。macOS 的 `dig` 可能按 `/etc/resolv.conf` 自己发查询，不能把它当成 Safari 或系统 resolver 的完全等价替身；用它测试硬编码 DNS 时应明确标注。

macOS 可先保存只读诊断：

```bash
scutil --dns
scutil --proxy
netstat -rn -f inet
netstat -rn -f inet6
```

如需抓包，根据实际活动网卡把 `en0` 换成正确接口，在系统 Terminal 中运行：

```bash
sudo tcpdump -i en0 -n '(udp port 53 or tcp port 53 or tcp port 853)'
```

并检查相关 `utun` 接口；单个接口没抓到 DNS 不等于不存在旁路。DoH 内容经 TLS 加密，看到 TCP/443 不能判断具体查询域名。日志、物理接口外发、隧道流量和可控域权威记录需要关联。iPhone 可从网关侧观察，不能凭 Mac 结果替代 iPhone 真机验证。

## 故障、引导与恢复

- **冷启动**：断开后重新连接，观察节点域名由独立阿里 DoH 解析；随后代理域名可用。检查节点使用 IPv4/IPv6 哪条路径。不要为了测试公开节点名称或密码。
- **节点失败**：在可恢复的测试环境临时阻断节点，使用未缓存的新域名。应代理业务失败，不能悄悄变成 DIRECT 或国内系统 DNS。国内直连业务及局域网应继续可用。恢复节点后复测。
- **主 DNS 失败**：受控地阻断 `1.1.1.1` 的代理出口访问，检查是否使用经代理的 `8.8.8.8`；同时阻断两者时，不应转成本地系统 DNS。代理端远程解析的协议可能完全不使用这些地址，必须记录实际模式。
- **国内 DNS 故障**：验证国内查询故障不会把业务自动切成代理。恢复网络 DNS 后可以重连恢复；不要求永久手改系统 DNS。
- **硬编码 DNS**：运行 `python3 scripts/probe_client_dns.py`。预期 IPv4 UDP DNS 返回 Fake-IP；未被接管的 TCP/IPv6 端口 53 查询没有上游答案。结合 `DST-PORT,53,REJECT` 的顺序、对照测试和日志判断；超时不能独立证明没有外发。私网旁路和应用 DoH/DoT 不在该端口保护的完整控制范围。
- **网络切换**：Wi-Fi ↔ 热点/蜂窝，观察新系统 DNS、节点引导和旧缓存恢复。重试国内、国外及 NAS 请求。iPhone 同样做 Wi-Fi ↔ 蜂窝。
- **微信图片/头像**：确认消息收发和图片加载分别正常；检查是否有公网 IPv6 请求长时间 SYN_SENT。已在本机确认关闭配置 IPv6 后头像/图片恢复，不能用文字消息正常替代资源加载验收。
- **IPv6 / NAT64**：当前默认 `ipv6=false`。若准备启用，先检查物理接口有可用公网 IPv6，并分别验证直连和代理；双栈网络测试 AAAA、国内 IPv6、境外 IPv6 和节点 IPv6；如日常使用 IPv6-only/NAT64 网络，再单独验收，当前 IP 字面量 DoH 的引导兼容性未得到真机证明。

通过标准：在“配置”模式，业务可用且命中预期策略；没有发现应代理域名通过非预期本地/国内 DNS 查询的证据；故障时不绕回直连；局域网仍可用。一次通过不构成所有版本、节点、网络下“100% 零泄漏”的承诺。

如未通过，保存时间、版本、请求域名、命中规则、DNS 上游和连接错误。区分节点握手失败、域名解析失败、规则命中错误与服务端地区拒绝，再有针对性修复。临时恢复备份配置即可，不必删除节点或更改其他应用。

## 2026-10-31 iPhone 蜂窝网络补充记录

用户报告的环境为 iOS 26.7.1、Shadowrocket 2.2.93（3488）、VLESS TCP TLS、Claude 原生 App；VPS 当前采用 IPv4 出口。用户在“设置 → 隧道”打开“包括所有网络”并重连后，在 5G 网络下完成测试：

- 提供的连接列表中，Claude 的 HTTPS 和 UDP 请求均标记为 `PROXY`，所示 Google、Sift、Sentry、Datadog 相关请求也选择代理。
- 用户确认 IPv4 测试显示预期出口，IPv6-only 测试无法打开。
- 结论仅为这次已连接状态的测试未发现 IPv6 绕过证据。日志只能记录被客户端观察到的连接；单个 IPv6 测试不可达，也可能来自测试站或路径故障，不能单独证明所有应用和协议均无泄漏。

“包括所有网络”是本机隧道设置，不由这份远程配置自动开启。“包括蜂窝服务”指 VoLTE、IMS、彩信等运营商服务，不是控制所有 5G App 数据流量。不要将手机有中国 IPv6 地址本身等同于 Claude 已看到该地址，也不要将 VPS 开启 IPv6 当成手机防旁路措施。

仍待实际完成：Wi-Fi ↔ 蜂窝切换、锁屏唤醒、节点不可用/重连、IPv6-only/NAT64 网络、可控目的端或物理接口的旁路验证。当时的修复没有改变 DNS 与 IPv4 兼容基线，也未代替用户操作手机；本轮候选改变了未知域名的解析触发条件，需要重新验证。

## 精确例外修订验收步骤

1. 在客户端“测试规则”里用 `0.cn.pool.ntp.org`、`account-cn.alibabacloud.com`、`www.hsbc.com.cn`、`swcdn.apple.com`、`officecdn.microsoft.com` 测试，应命中前置经审查 DIRECT。
2. `0.pool.ntp.org`、`0.jp.pool.ntp.org`、`api.alibabacloud.com`、`tv.apple.com`、`news.apple.com`、`copilot.microsoft.com`、`claude.ai` 继续 PROXY。不得仅为 `.cn` 或国内品牌批量切换整个分类。
3. 运行 `python3 scripts/probe_client_services.py --output .build/client-services.json`。NTP 必须收到匹配请求时间戳的 UDP/123 应答；脚本不调整系统时间。CDN 根路径的 400/404 只表示收到了协议响应，不是完整安装包下载认证。
4. 查看原生连接日志核对实际 DIRECT/PROXY 和耗时。静态模型不是实际出口证明。路由器应在连接该品牌本地网络时验证，错误的本地 DNS/DHCP 不由规则修复。
5. 手机只需继续使用原订阅地址。新规则没有增加客户端远程 RULE-SET；是否刷新及何时刷新由客户端决定。未在 iPhone 上逐项完成新增例外真机验收。
